# SKILL IS NOT DOCUMENT: A QUERY-CONDITIONAL BENCH-MARK AND TWO-STAGE RETRIEVER FOR LLM AGENT SKILL ROUTING

ABSTRACT 

LLM agents complete complex tasks by composing multiple skills, and skill re-trieval is a front-end stage for agents. Skill retrieval needs a different training signal from document retrieval: top-K joint correctness depends not only on the seman-tic relevance of each individual query–skill pair, but also on whether the skills retrieved together can collaborate to fulfill the task under the given query. This “skill compatibility” cannot be derived from independent relevance alone. Yet ex-isting LLM-based data synthesis pipelines can produce a direct supervision sig-nal for “which skills should not be jointly retrieved under this query”—namely the LLM’s own rejection decisions—and this signal is routinely discarded as low-quality data. To address this gap, we propose Reject-as-Resource Retriever (R3) and construct R3-Skill, a bilingual (Chinese–English) skill retrieval benchmark targeting realistic agent skill routing. R3-Skill spans four language directions, fea-tures query phrasings close to real user requests, and is verified through multi-expert cross-checking. The dataset contains 10,246 skills grouped into 8 thematic super-domains; 41,592 accepted queries; and 32,828 LLM-rejected annotations, further organized into an 8-class rejection-reason taxonomy. Unlike prior datasets, R3-Skill keeps the rejection signal that is usually thrown away, and uses it as neg-ative supervision for compatibility. On R3-Skill, we build a two-stage retrieval system comprising R3-Embedding and R3-Reranker, with skill compatibility in-corporated as an explicit training signal. We analyze this signal at the gradient level: in the bi-encoder, the representation of any single skill is jointly determined by multiple queries, so the “push-away” gradient injected by the compatibility sig-nal is diluted by bilateral balancing and contributes little at the recall stage; in the cross-encoder, each query–skill pair is scored independently, so the compatibility signal can be used as graded supervision for ranking without loss. We therefore place the compatibility signal at the cross-encoder stage, and ablation studies on two datasets confirm this choice. The R3-Embedding + R3-Reranker pipeline at-tains Hit@1 = 0.7714, NDCG@10 = 0.8327 and Set-Compat = 0.3525 on R3-Skill. The dataset, training code and model weights are released as open source for agent skill routing.

Skills have since been adopted by major agent platforms such as Claude Code, Codex and Gemini CLI, and the community has accumulated tens to hundreds of thousands of skills within months Anthropic (2025). Recent surveys Xu & Yan (2026); Jiang et al. (2026) position skills as the third paradigm of agent capability extension, following prompt engineering and tool use. A skill and a tool are not the same kind of object: a tool is an atomic “input → call → output” function, whereas a skill teaches the agent how to handle a class of problems—covering call constraints, multi-step procedures, canonical code and edge cases. Memento-Skills Zhou et al. (2026) further shows that, when the skill library is treated as continuously updatable agent memory, improvements to the skills themselves yield 26.2% / 116.2% relative accuracy gains on GAIA / HLE respectively. Completing a complex task typically requires several skills working together—for example, “transcribe this meet-ing recording and then summarize the key takeaways” calls for a speech-to-text skill followed by a summarization skill, and a missing or mismatched skill can cause the task to fail. 

What does a skill look like? A typical skill contains: • name : a short identifier, e.g. SendGrid Email Send ;• description : a one-line purpose, e.g. “Send transactional emails through SendGrid”; • body : detailed call instructions (API shape, parameter constraints, platform dependencies, best practices, canonical code), typically tens to hundreds of lines. 1.2 WHY SKILL RETRIEVAL MATTERS The intuitive approach is to place all skills in the prompt and let the LLM choose. This is not viable in real agent deployments: (A) The skill inventory keeps growing. Public skill repositories have expanded from ~36K skills indexed by SkillFlow Tagkopoulos et al. (2025), ~26K in SRA-Bench Su et al. (2026), and 280K+ reported by AgentSkillOS Li et al. (2026a), to even larger public corpora. As skill counts grow from dozens to thousands or tens of thousands, an “all-prompt” approach runs into three problems: token cost, inference latency and context-length limits. Prior work also shows the limits of injecting full skill sets directly into the inference context: this approach brings in large amounts of irrelevant context, and the model can only use these skills while reading them, rather than absorbing them as its own capability Lu et al. (2026). (B) Skills are highly similar; descriptions alone do not separate them. Take transactional email skills: SendGrid, Mailgun and Postmark are independent skills but their descriptions are almost identical—“Send transactional emails”. The differences are buried in the body: SendGrid empha-sizes enterprise-scale, high-throughput infrastructure; Mailgun highlights developer flexibility and 2webhook callbacks; Postmark physically isolates transactional and marketing email to protect deliv-erability (Message Streams). When a user asks “isolate marketing from transactional email while preserving deliverability”, the retriever must read the body to pick Postmark. Prior work validates this directly on a ~80K skill pool: hiding the skill body lowers routing accuracy by 31–44 percent-age points Zheng et al. (2026), which shows that the routing signal lives in the body rather than the metadata. (C) Multi-skill routing demands “minimal yet sufficient”. For each query the agent needs the right set of skills: a missing skill makes the task unsolvable, and a conflicting one creates new failures. SkillsBench provides a direct quantification: curated skills improve overall pass rate by +16.2pp, but 16 of 84 tasks show performance regressions Li et al. (2026b); Skills in the Wild further reports diminishing returns under more realistic settings Liu et al. (2026); CoEvoSkills also observes that human-authored skills bring substantially uneven gains across domains, with clear regressions in some Zhang et al. (2026). The retriever must therefore both return the right candidates and order them well, since their positions in the top-K shape downstream call success. (D) Sandbox provisioning cost in real deployments. In production agent platforms, concurrent users typically share an agent through per-session sandboxes: a sandbox is created when a user starts a session and is reclaimed by a periodic sweep after the session has been idle for some time, so a one-sandbox-per-user model is infeasible. Each sandbox must install the skills it actually needs before the agent can run. If every sandbox loads the full skill library, the install / reset latency grows roughly linearly with the library size and quickly dominates the user-perceived cold-start time. Routing only the K skills each sandbox actually needs is therefore an engineering requirement, not just a quality issue. 1.3 SKILL RETRIEVAL ̸ = DOCUMENT RETRIEVAL Document retrieval typically assumes that “two documents being retrieved together for the same query” is harmless—if both are relevant, returning them together introduces no error. Skill retrieval is different. The retriever returns a set of capabilities the agent will actually invoke. Whether two skills can run together under a particular query depends on the query itself; a different query over the same pair can flip the verdict (Figure 2). “Whether two skills should be jointly retrieved” is therefore not a global binary relation between skills, but must be assessed under a given query. Concurrent work Skill-RAG also points out that the bottleneck of many hard cases in RAG lies not in missing evidence but in a structural alignment gap between the query and the evidence space, which motivates its post-hoc skill selection mechanism Wei et al. (2026). We focus on the retrieval stage itself: in the training objective, “relevance” should depend on the specific query rather than be determined by the skill alone. We estimate an empirical proxy for this constraint on real data in §2.3. 1.4 STATUS QUO AND GAPS IN SKILL RETRIEVAL DATASETS Adding skill compatibility into the training objective is mainly limited by the lack of suitable training data. Existing skill retrieval datasets fall roughly into two categories: (i) end-to-end task benchmarks—SkillsBench, SRA-Bench, SkillFlow—which mainly target the post-retrieval incorpo-ration/application stage and lack the scale to train a retriever; (ii) training resources designed specif-ically for skill retrieval Cho et al. (2026). Both inherit the contrastive paradigm from document re-trieval (the DPR Karpukhin et al. (2020) / ANCE Xiong et al. (2020) / RocketQA Qu et al. (2021) line, with BM25 Robertson & Zaragoza (2009) as a sparse baseline) and are fairly mature on document retrieval. Toward the goal of agent skill routing, however, three gaps remain: 1. LLM rejection signal is discarded. Existing query–skill synthesis pipelines drop a sample as soon as the LLM judges a skill set “not naturally combinable”—yet this is precisely where compatibility-oriented negatives are densest. 2. Cross-lingual coverage is lacking. Existing skill retrieval resources cover English only. Clus-ter analysis of 26,502 public skills on the ClawHub platform by Red Skills or Blue Skills shows that English skills lean toward capability modules while Chinese skills lean toward scenario packaging Hu et al. (2026)—meaning that the linguistic asymmetry of “a Chinese query retrieving English skills” is worse in real deployments. While multilingual retrievers (e.g. BGE-M3 Chen et al. (2024)) achieve query–document-level Chinese–English align-ment, existing datasets still do not provide a training signal for cross-lingual skill compati-bility under given queries. 3. Test-set query phrasing diverges from real user requests. Queries generated by LLMs under structured prompts tend to be long, formal, and dense with technical terms, so a retriever can score well just by matching keywords. Skills in the Wild reports a similar phenomenon: when the agent must self-retrieve from a 34k real skill pool with progressively more realistic test settings, pass rate drops with difficulty and approaches a no-skill baseline at the strictest setting. 4This work targets the three gaps above: we build R3-Skill, retain LLM-judged non-co-executable samples as supervision for skill compatibility, cover four query language directions across Chinese and English, and apply LLM rewriting to the test queries to better resemble real user requests. On top of this dataset we train two retrieval models, R3-Embedding and R3-Reranker. 1.5 CONTRIBUTIONS Our contributions: • C1 (theory): a formal decomposition of top-K joint correctness in skill retrieval into a rel-evance factor and a skill-compatibility factor (with the dual-encoder gradient analysis in Appendix B). • C2 (data): R3-Skill, a benchmark with 10,246 skills, 41,592 accepted queries, and 32,828 SKIP annotations, covering 4 query language directions and 6 query styles, with test queries close to real user requests and verified by multiple experts. • C3 (method): a two-stage retrieval system—R3-Embedding trained with standard InfoNCE; R3-Reranker, on a cross-encoder, encodes SKIP partners as a graded label and optimizes ranking directly via a listwise CE objective. • C4 (empirical): we open-source the two-stage models R3-Embedding and R3-Reranker, achieving Hit@1 = 0.7714, NDCG@10 = 0.8327 and Set-Compat = 0.3525 on R3-Skill, available for use in agent skill routing.

2.3 NEAR-NEIGHBOR HARD-CONSTRAINT SAMPLING Sampling skill combinations uniformly at random produces SKIP instances that are mostly easy: two skills are completely unrelated and trivially distinguishable without any training. Learning skill compatibility requires harder negatives: semantically similar skill combinations that nevertheless cannot be jointly executed under the query. We encode skill text with BGE-M3 and run KMeans for 

K ∈ { 10 , 20 , 30 , 40 }, comparing parameter choices via clustering quality and human spot-checking; we settle on K = 40 , then merge the 40 sub-clusters into 8 super-domains. Cluster quality curves across K and the K = 40 hierarchy of 8 super-domains × 40 sub-clusters are deferred to Figures 5 and 6 in the appendix. 3 METHOD 

R3-Skill provides two kinds of supervision: WRITE indicates a skill set that can complete a task under some query; SKIP indicates a skill set that was sampled together but judged by the LLM as unable to co-occur naturally. We train a two-stage pipeline: R3-Embedding (bi-encoder, fine-tuned from Qwen3-Embedding-0.6B) does coarse recall over the full skill pool; R3-Reranker (cross-encoder, fine-tuned from Qwen3-Reranker-0.6B) reranks the recalled candidates.

Why SKIP belongs to the cross-encoder. SKIP partners could in principle also enter the Stage-1 InfoNCE pool, but this does not help. A single shared e(s′) is governed by every query in which 

s′ appears: under a query q where s′ is a SKIP partner, the gradient pushes e(s′) away from e(q);under another query ˜q where s′ is a positive, it is pulled back toward e(˜ q). The push is fractional (ps′ ≪ 1 in a multi-candidate pool) while the pull is near unit-strength, so the SKIP signal is largely cancelled at the bi-encoder. R3-Reranker (cross-encoder) avoids this because each (q, s ) pair is scored independently, so SKIP can be carried as a graded label without dilution. Cross-lingual rejection patterns and where the reranker helps. en2zh is both the most common and the most difficult direction in deployment (English skills + Chinese queries). 5 CONCLUSION AND DISCUSSION 

We identify a difference between skill retrieval and document retrieval in top-K joint correctness: skill retrieval is also limited by skill compatibility, and this constraint is itself query-dependent. We keep LLM-rejected samples as negative supervision, build R3-Skill—a skill retrieval benchmark covering four Chinese–English language directions and verified by multiple experts—and train two matched-stage models, R3-Embedding and R3-Reranker. On R3-Skill, the two-stage system reaches Hit@1 = 0.7714, NDCG@10 = 0.8327 and Set-Compat = 0.3525, with the largest gain on Set-Compat. The R3-Skill dataset and the two-stage model weights are released as open source for agent skill routing. 

Limitations and future work. Several aspects remain open: (i) Chinese skills are sparse (246 en-tries), reflecting the current state of public ecosystems; expanding the Chinese skill pool is a direct next step. (ii) The skill-compatibility oracle relies on LLM annotation; cross-source LLMs and multi-expert verification on the test set provide two safeguards, but consistency remains bounded by LLM judgment, and expert annotation of the training set would be more reliable. (iii) Finer-grained stress slicing by rejection reason, near-neighbor geometric distance, or multi-skill joint degree ( k = 1/2/3 )is left to future work. (iv) Test-set verification was performed by our team; bringing in annotators from more diverse backgrounds, or a third-party blind cross-check, would be a valuable extension. (v) This work focuses on offline retrieval performance; real deployments involve query-phrasing drift across entry points, business-side metrics (CTR, call success, task completion, user rewrite rate), user-profile-aware ranking, and end-to-end retrieval-to-completion transmission—SRA-Bench 10 already shows that retrieval hits do not automatically translate into downstream completion. (vi) The reranker pool is fixed at top-20 due to engineering budget; whether expanding the pool to 50 / 100 further improves Set-Compat is left to future work.

D.1 Style Descriptions (6 styles, bilingual) 

Chinese style descriptions (used by zh2zh / en2zh). 

task_direct: 任务直述：开门见山地告诉模型要做什么，可以省略主语，像在下指令。 

scene: 场景描述：先简短交代背景或痛点，再引出需求；不要使用 "作为某某 "的句式。 

role_setup: 角色设定：让模型扮演某个专家身份再来帮你， 例如 "你是一名资深 X，请帮我 ..." 。

constraint: 约束条件式：把目标 + 输入 + 输出格式 / 风格 / 长度 / 限制条件等讲清楚。 

multi_step: 多步骤式：把需求拆成 2~4 个有先后的小步骤，让模型按顺序处理。 

debug: 排错求助式：贴一段疑似有问题的代码 / 配置 / 报错，让模型定位并修复 （也可以只描述现象） 。

English style descriptions (used by en2en / zh2en). 

task_direct: Task-direct: state the task plainly, like an instruction. scene: Scene-first: briefly describe a context or pain point before stating the need; avoid 'As a ...' phrasing. role_setup: Role-setup: ask the model to act as some expert (e.g., 'You are asenior X, please help me ...'). constraint: Constraint-style: spell out goal + input + output format / style /length / constraints. multi_step: Multi-step: break the request into 2~4 ordered substeps for the model to handle in sequence. debug: Debug-help: paste suspected-broken code / config / error and ask for diagnosis and fix (description-only is fine).

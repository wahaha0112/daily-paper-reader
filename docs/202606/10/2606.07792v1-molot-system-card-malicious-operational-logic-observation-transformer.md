## 摘要
MOLOT（恶意操作逻辑观察转换器）是一种针对静态应用安全测试（SAST）环境设计的静态恶意代码检测系统，在该环境中包元数据、维护者历史记录和动态执行轨迹可能不可用或不可靠。该系统将源代码表示为从静态调用图导出的行为序列，并包含一个解释阶段，该阶段对可疑行为活动进行排序并将其映射回源代码位置。该方法在来自PyPI和npm的Python和JavaScript包上进行了评估，与开源检测工具进行了比较，并在实际审核工作流程中观察到的运行时、内存使用和误报率等产品约束下进行了验证。我们还发布了Open Malicious-Code Bench，这是一个用于可重复评估恶意包检测方法的公开基准测试。结果表明，静态行为序列建模可以为现代DevSecOps工作流程提供准确、可解释且可部署的恶意代码检测。

## Abstract
MOLOT (Malicious Operational Logic Observation Transformer) is a static malicious-code detection system designed for SAST setup where package metadata, maintainer history, and dynamic execution traces may be unavailable or unreliable. The system represents source code as behavior sequences derived from static call graphs, includes an explanation stage that ranks suspicious behavior activities and maps them back to source-code locations. The approach is evaluated on Python and JavaScript packages from PyPI and npm, compared with opensource detection tools, and validated under product constraints including runtime, memory use, and false-positive rates observed in a real moderation workflow. We also release Open Malicious-Code Bench, a public benchmark for reproducible evaluation of malicious-package detection methods. The results show that static behavior-sequence modeling can provide accurate, explainable, and deployable malicious-code detection for modern DevSecOps workflows.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **核心问题**：在软件供应链安全中，恶意代码（CWE-506）不断通过嵌入合法项目（如 LiteLLM 的 `litellm_init.pth`、Shai-Hulud 2.0 的 `setup_bun.js`）造成攻击。现有的恶意包检测系统高度依赖包元数据、维护者历史、注册表流行度或动态执行轨迹，这些信号在 SAST（静态应用安全测试）场景下（例如私有、未发布、内部仓库的包，或攻击者通过盗用合法账号注入恶意逻辑时）往往不可用或不可靠。
- **整体含义**：提出 **MOLOT**，一种**纯静态、不依赖元数据**的恶意代码检测系统，通过将源代码表示为从**静态调用图**提取的**行为序列**，并用 BERT 进行分类，同时提供基于 SHAP 的可解释性，将可疑活动映射回源码位置。系统旨在适用于现代 DevSecOps 工作流，兼准确性与可部署性。

## 2. 论文提出的方法论：核心思想、关键技术细节

### 核心思想
- 用**静态调用图**描述项目的行为，将调用链转化为文本序列（行为活动链），训练 BERT 模型进行二元分类（恶意/良性），并用 SHAP 解释模型判定中贡献最大的活动。

### 关键技术细节（五阶段流水线，见图 1）

1. **提取调用图**：使用 PT Application Inspector SAST 引擎提取每个函数调用的位置、参数、所在函数，并捕获字面量赋值（用于保留关键参数值）。
2. **遍历调用图构建链**：从无入边的入口点出发，按执行顺序生成函数调用链。处理循环（跳过自调用和已访问函数），并将遍历限制在单个文件范围内（配合后续文件级分类）。
3. **将链渲染为文本**：将每个调用映射为活动类别（如 `use_network_module`、`create_process`）。未分类的调用被折叠为填充标记（如 `few / some / many padding activities`），以保留位置信息。链按执行时机（安装时、模块导入时、其他）排序拼接。
4. **BERT 分类**：文本送入 BERT-base-uncased 分类器，输出恶意/良性标签。
5. **SHAP 解释**：对标记为恶意的样本，使用 SHAP（masker 按活动边界划分 token），计算每个活动对恶意类的贡献 $s_i = shap_i(mal) - shap_i(benign)$，返回 top-*k* 个正贡献活动及其源码位置。

### 关键改进（相对于基线 CEREBRO）
- **文件级分类**：缓解上下文窗口限制；包级预测通过 OR 聚合文件标签。
- **去除文件/入口点名称**：防止模型过拟合于名称中的子串（如 `session` 导致假阴性）。
- **增强文本表示**：保留参数中的行为信息，使用填充标记反映未分类调用的稀疏性。

## 8. 不足与局限

- **仅支持 Python 和 JavaScript**：扩展其他语言需要语言专用的特征提取器（调用图构建和活动类别定义），虽然模型本身可复用。
- **LLM 辅助标注精度有限**：行级 IoU 约 55-60%，不足以训练更细粒度的模型（如图神经网络）。
- **调用图提取是性能瓶颈**：最长单包达 182 s（CPU），难以应对每日数十万 release 的高通量场景。
- **对混淆代码脆弱**：论文提到多数误分类源于混淆导致调用图不完整。
- **未明确训练资源**：缺乏模型训练的具体 GPU 型号、时长、超参数等细节，复现成本稍高。
- **真实部署误报率尚可但仍有改进空间**：包级 9.24% 误报对审核人员造成一定负担。
- **仅评估静态 SAST 场景**：未与动态分析（如 DySec）或纯 LLM 方法（如 SecurityAI）直接比较，优势仅在限定场景下成立。

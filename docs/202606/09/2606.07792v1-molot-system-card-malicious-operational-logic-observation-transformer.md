## 摘要
MOLOT（恶意操作逻辑观察变换器）是一种静态恶意代码检测系统，专为SAST（静态应用安全测试）场景设计，在该场景中包元数据、维护者历史记录和动态执行轨迹可能不可用或不可靠。该系统将源代码表示为从静态调用图导出的行为序列，并包含一个解释阶段，用于对可疑行为活动进行排序并将其映射回源代码位置。该方法在来自PyPI和npm的Python和JavaScript包上进行了评估，与开源检测工具进行了比较，并在产品约束（包括运行时、内存使用以及在实际审核工作流中观察到的误报率）下进行了验证。我们还发布了Open Malicious-Code Bench，这是一个用于可重复评估恶意包检测方法的公共基准。结果表明，静态行为序列建模可以为现代DevSecOps工作流提供准确、可解释且可部署的恶意代码检测。

## Abstract
MOLOT (Malicious Operational Logic Observation Transformer) is a static malicious-code detection system designed for SAST setup where package metadata, maintainer history, and dynamic execution traces may be unavailable or unreliable. The system represents source code as behavior sequences derived from static call graphs, includes an explanation stage that ranks suspicious behavior activities and maps them back to source-code locations. The approach is evaluated on Python and JavaScript packages from PyPI and npm, compared with opensource detection tools, and validated under product constraints including runtime, memory use, and false-positive rates observed in a real moderation workflow. We also release Open Malicious-Code Bench, a public benchmark for reproducible evaluation of malicious-package detection methods. The results show that static behavior-sequence modeling can provide accurate, explainable, and deployable malicious-code detection for modern DevSecOps workflows.

## 1. 核心问题与整体含义（研究动机和背景）

- **问题**：软件供应链攻击日益严重，攻击者利用恶意代码（CWE-506）嵌入合法项目。现有恶意包检测方法通常依赖包元数据、维护者历史、注册表流行度或动态执行轨迹，这些信号在**静态应用安全测试（SAST）** 场景下不可靠或不可用——包可能是私有的、未发布、刚克隆的，或属于内部仓库。此外，元数据可能因账户被攻陷而失效。
- **动机**：需要一种**纯静态**、不依赖元数据或执行的恶意代码检测方法，能够分析源代码本身，并且结果应当**可解释**，以便安全工程师直接定位可疑代码。
- **意义**：MOLOT 为 DevSecOps 流程提供了一种准确、可解释且可部署的静态检测方案，并开源了统一基准，推动该领域可复现研究。

## 2. 方法论

### 核心思想
将源代码通过静态调用图转换为行为序列（自然语言描述的代码活动），使用 BERT 模型分类，并用 SHAP 解释哪些活动导致恶意判定。

### 关键技术细节
1. **调用图提取**：使用 PT Application Inspector SAST 引擎提取调用图，记录每个函数调用的位置、参数、字面量赋值。
2. **链构建**：从入口点（无入边顶点）出发，遍历调用图得到函数调用链；排除递归和循环；限定在单个文件内。
3. **文本渲染**：
   - 将每个调用映射为活动类型（如 `use_network_module`、`create_process`）。
   - 非活动类调用被压缩为填充标记（`few/some/many padding activities`），保留位置信息。
   - 保留关键字面量参数（URL、Base64等），增加多样性。
   - 链条按执行时机排序（安装时→导入时→其他），拼接成文档。
4. **分类**：BERT-Base 模型对每个文件的序列输出二分类（恶意/良性）。包级别聚合采用 OR 策略（任一文件为恶意则整个包为恶意）。
5. **解释**：对恶意样本应用 SHAP，按活动边界划分 token，计算每个活动对恶意类的贡献差值 `s_i = shap_i(mal) - shap_i(benign)`，返回 top-k 正贡献活动及其源代码位置（文件+行号）。
6. **文件级标注**：先由专家标注少量文件，再用 LLM（Llama 3.3 70B / GPT-OSS 120B）进行大规模标注，作为训练 BERT 的监督信号。

### 公式/算法流程（文字说明）
```
输入：项目源代码
1. SAST引擎 → 调用图（含元数据）
2. 遍历调用图 → 行为链（去重、限单文件、去递归）
3. 映射为文本序列（活动类 + 参数 + 填充标记）
4. BERT 分类器 → 恶意/良性概率
5. 若为恶意：SHAP 计算活动贡献 → 输出 top-k 可疑位置
输出：包级标签 + 解释列表
```

## 6. 主要结论与发现

- 静态行为序列建模（MOLOT）在**SAST 场景**下显著优于传统规则工具，F1 分数在包级和文件级均最高。
- 关键改进：去除文件/函数名（避免过拟合）、添加 padding 标记（丰富位置信息）、保留参数字面量（增加序列多样性）。
- 联合训练 Python + JavaScript 的单一模型在两个语言上都能达到接近语言专用模型的效果。
- SHAP 解释能够有效定位恶意代码行（IoU ~0.75），正贡献 top-k 选择策略在精度和召回间取得平衡。
- 性能可部署：GPU 下完整管道约几十秒/包，CPU 下 SHAP 解释为瓶颈但仍在可接受范围。
- 实际部署 2 个月的误报率（包级 9.24%）符合产品要求。
